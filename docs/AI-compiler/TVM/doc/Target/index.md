# Apache TVM Target

## 摘要

Target（编译目标）是 Apache TVM 编译栈的核心配置对象，用于定义模型部署的硬件环境、指定代码生成后端与运行时约束，驱动从高层计算图到底层硬件代码的全流程定向优化。它是TVM实现「一次模型定义，多硬件部署」能力的核心机制，同一份Relax/Relay计算图可通过指定不同Target，编译生成适配不同硬件架构的可执行代码。

## 1 核心功能

Target 贯穿编译全流程，核心承担四类职能：

### 1.1 硬件描述与定向优化

提供目标设备的完整硬件特征描述，包括CPU架构、GPU计算能力、加速器指令集、内存层次结构、核心数量等参数，支撑编译器执行硬件专属的调度优化，如循环分块尺寸、向量化宽度、线程块配置、内存复用策略等。

### 1.2 代码生成后端路由

指定编译过程调用的后端代码生成器（如LLVM、CUDA、OpenCL等），负责将中间表示（IR）降级为对应硬件的可执行机器码或源代码。不同后端对应不同的硬件生态与指令集，Target是编译器选择后端的唯一依据。

### 1.3 异构环境隔离

支持Host（主机）与Device（设备）双目标分离，区分编译宿主环境与目标执行环境，是交叉编译、异构计算场景的核心支撑。主机端负责调度与内存管理，设备端负责计算密集型算子执行，二者可独立指定目标架构。

### 1.4 全栈优化驱动

Target的硬件特征会反向驱动两级IR的优化策略：

- 图级IR阶段：决定算子融合阈值、内存布局转换、算子合法化映射规则
- 算子级IR阶段：指导循环分块、并行映射、指令集匹配等调度优化

## 2 主流 Target 类型

TVM官方支持覆盖CPU、GPU、嵌入式加速器等多类硬件的目标类型，核心分类如下：

### 2.1 CPU类目标

| Target标识 | 技术说明                                                     | 常用配置参数                                                                                               |
| -------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `llvm`   | 通用CPU后端，基于LLVM编译器基础设施生成机器码，原生支持x86、ARM、RISC-V等所有LLVM兼容架构 | `-mcpu=skylake-avx512`：指定CPU型号与指令集　`-mtriple=aarch64-linux-gnu`：交叉编译目标三元组　`-num-threads=8`：运行时CPU线程数 |
| `c`      | 纯C源代码后端，生成可移植的标准C代码，适配无LLVM支持的嵌入式、微控制器场景                 | -                                                                                                    |

### 2.2 GPU类目标

| Target标识           | 对应硬件平台                                   | 常用配置参数                                    |
| ------------------ | ---------------------------------------- | ----------------------------------------- |
| `cuda`             | NVIDIA GPU，生成CUDA核函数，适配桌面端、数据中心级NVIDIA显卡 | `-arch=sm_80`：指定GPU架构版本（如Ampere架构对应sm_80） |
| `rocm`             | AMD GPU，基于ROCm计算平台，适配AMD数据中心与消费级显卡       | -                                         |
| `opencl`           | 通用OpenCL计算设备，支持各类GPU、FPGA、嵌入式加速器         | `-device=adreno`：指定高通Adreno移动GPU          |
| `metal`            | 苹果Apple Silicon GPU，适配macOS、iOS等苹果生态设备   | -                                         |
| `vulkan`           | 跨平台Vulkan计算后端，同时支持移动端与桌面端GPU             | -                                         |
| `webgpu`           | 浏览器端WebGPU计算后端，适配Web端推理场景                | -                                         |
| `mali` / `bifrost` | ARM Mali系列移动GPU，适配移动端嵌入式场景               | -                                         |

### 2.3 嵌入式与专用加速器

- `hexagon`：高通Hexagon DSP，适配移动端低功耗计算场景
- `stm32`：STM32系列微控制器，属于microTVM嵌入式生态
- `arm_compute_lib`：ARM Compute Library算子加速库，以BYOC模式接入
- `tensorrt` / `cudnn`：NVIDIA TensorRT / cuDNN推理引擎，以BYOC扩展模式接入
- 第三方NPU/DPU目标：如赛灵思Vitis AI DPU等厂商定制加速目标

## 3 Host-Device 双目标架构

TVM采用**主机目标+设备目标**的两级目标模型，原生支持**异构计算**与**交叉编译**，是其适配复杂部署环境的核心设计。

### 3.1 角色分工

- **Device Target（设备端目标）**：面向加速器（GPU/NPU/DSP等），负责生成计算密集型算子的设备端核函数，决定算子执行的性能。
- **Host Target（主机端目标）**：面向主CPU，负责生成内存管理、算子调度、流程控制等主机端控制代码，决定整体**调度效率**。

### 3.2 典型应用场景

1. **交叉编译场景**：在x86开发主机上编译ARM边缘设备的可执行代码，Host Target指定ARM架构目标三元组，编译完成后将产物部署到边缘设备运行。
2. **异构推理场景**：NVIDIA GPU推理部署时，Device Target设为cuda生成GPU核函数，Host Target设为llvm生成CPU调度代码，二者协同完成端到端推理。

### 3.3 代码示例

```
import tvm

# 定义主机端目标：ARM64架构Linux系统CPU
target_host = tvm.target.Target("llvm -mtriple=aarch64-linux-gnu")
# 定义设备端目标：NVIDIA Ampere架构GPU，关联主机目标
target_device = tvm.target.Target("cuda -arch=sm_80", host=target_host)
```

## 4 Host-Device 双目标架构的设计背景

Host-Device 双目标架构并非孤立的设计，而是**硬件异构化趋势、软件语义分层、全场景部署需求、TVM 自身架构演进**共同驱动的必然结果，本质是将经典编译原理中「目标机」的概念，细化为「**控制侧目标机** + **计算侧目标机**」的两级结构，适配**异构计算**时代的编译需求。

### 4.1 硬件产业背景：异构计算成为AI部署的标准范式

#### 4.1.1 算力分工的固化：通用CPU + 专用加速器

AI 模型的计算特征天然形成了两层分工，直接决定了硬件的异构形态：

- **计算密集型张量运算**：矩阵乘、卷积、向量元素操作等，数据并行度高、控制逻辑简单，适合由 GPU、NPU、DSP、TPU 等专用加速器执行，追求高吞吐量、高算力密度。
- **控制与调度逻辑**：内存分配与拷贝、驱动调用、流程控制、分支判断、动态形状处理、前后预处理等，串行性强、逻辑复杂，适合由通用 CPU 执行，追求低延迟、强通用性。

这种分工是整个行业的事实标准：从数据中心的「x86 CPU + NVIDIA GPU」，到边缘端的「ARM CPU + NPU/DSP」，再到端侧手机的「ARM CPU + Mali/Adreno GPU」，无一例外都是异构组合。单一指令集的硬件无法同时兼顾计算效率与控制灵活性，这是双目标架构最底层的硬件基础。

#### 4.1.2 单目标编译的天然缺陷

如果编译器只支持单一目标，会直接出现两个不可调和的问题：

- 若目标为加速器：只能生成计算核函数，主机侧的控制、调度、内存管理逻辑只能靠手写胶水代码对接，既无法做编译期优化，也无法保证跨架构兼容性。
- 若目标为CPU：无法利用加速器的算力，模型推理性能差一个数量级，完全丧失AI加速的意义。

双目标架构的核心设计初衷，就是**让编译器同时面向两个不同的目标机生成代码，分别负责控制逻辑与计算逻辑，二者协同完成端到端推理**。

### 4.2 软件语义背景：计算流与控制流的天然分层

#### 4.2.1 深度学习模型的语义分层

深度学习模型的代码语义天然分为两个层级，对应不同的执行载体：

- **算子级计算流**：纯数据并行、无副作用的张量运算，是模型的核心计算主体，适合卸载到加速器执行。
- **图级控制流**：条件分支、循环、动态形状推导、内存布局转换、算子调度、错误处理等，属于控制逻辑，串行执行且存在副作用，更适合在通用CPU上运行。

#### 4.2.2 与TVM两级IR架构的对应

TVM 的 Relax（图级IR）+ TensorIR（算子级IR）两层架构，天然匹配这种语义分层，也直接要求双目标编译的支撑：

- **Relax 层**：负责描述计算图拓扑、控制流、内存布局，其编译优化与代码生成对应**主机侧目标**——决定算子如何调度、内存如何管理、控制流如何执行。
- **TensorIR 层**：负责描述算子内部的循环结构、并行映射、指令匹配，其编译优化与代码生成对应**设备侧目标**——决定单个算子如何在加速器上高效执行。

如果没有双目标架构，两层IR就只能面向同一种硬件，既浪费了图级IR对控制逻辑的优化能力，也限制了算子级IR对加速器的深度适配。

#### 4.2.3 算子卸载（Offloading）的标准化

**异构计算**的核心是「计算卸载」：把适合加速器的算子从主机逻辑中剥离，放到**设备端**执行。**双目标架构**为卸载提供了标准化的编译边界：

- 编译期自动标记可卸载算子，按目标拆分**编译单元**；
- 主机侧生成卸载调度、数据收发的代码；
- **设备侧**生成算子核函数代码；
- 两侧通过标准运行时接口交互，无需手动胶水代码。

### 4.3 工程部署背景：交叉编译与全场景部署的刚需

#### 4.3.1 开发与部署环境的分离

AI 部署的典型工程范式是「中心化编译，分布式部署」：

- 编译环境：通常是x86架构的高性能开发服务器，算力充足、工具链完整；
- 部署环境：可能是ARM架构的边缘板卡、嵌入式设备、手机端，算力有限、环境受限，不具备本地编译能力。

这就要求编译器必须支持**交叉编译**：在一种架构的主机上，编译出另一种架构的可执行代码。

- 传统单目标交叉编译只能解决「设备端代码」的跨架构生成，忽略了「主机端控制代码」也需要匹配部署端的CPU架构。
- 双目标架构可以同时指定主机端目标架构与设备端目标架构，一次性编译出完整的、可直接在目标**异构环境**运行的程序。

#### 4.3.2 嵌入式与端侧部署的强约束

在嵌入式、物联网、端侧场景下，部署环境的约束极强：

- 硬件资源受限，无法安装完整的编译工具链与依赖库；
- CPU 架构多样（ARMv7、ARMv8、RISC-V等），搭配的加速器类型千差万别；
- 对二进制体积、启动延迟、内存占用有严格要求。

**双目标架构**可以精准匹配每一种「CPU + 加速器」的硬件组合，针对目标环境做极致优化，同时完全不需要部署端具备编译能力，这是TVM能够覆盖全场景部署的核心工程基础。

### 4.4 TVM自身架构演进的必然结果

#### 4.4.1 早期单目标架构的局限

TVM 早期版本只支持单一目标配置，存在三个明显缺陷：

1. **主机侧架构默认绑定本地系统**：编译时自动使用编译机的CPU架构作为主机端目标，交叉编译场景下会生成错误架构的主机代码，无法在部署端运行。
2. **主机侧代码无优化**：主机侧的内存管理、调度逻辑、驱动交互代码默认生成，不做针对性优化，经常成为端到端推理的性能瓶颈。
3. **异构组合扩展性差**：每新增一种「CPU + 加速器」组合，都需要修改编译流程代码，无法通过配置化的方式快速适配。

#### 4.4.2 运行时分层设计的倒逼

TVM 的运行时（Runtime）本身就是分层设计：

- **主机运行时**：负责模块管理、函数调度、内存分配、设备驱动抽象，运行在通用CPU上；
- **设备运行时**：负责核函数执行、设备内存管理，运行在加速器上。

编译作为运行时的上游，必须对应分层的运行时架构，分别生成适配两侧的目标代码，否则运行时的分层设计就失去了编译优化的支撑。双目标架构本质是「分层运行时」在编译期的镜像。

#### 4.4.3 全硬件生态覆盖的定位

TVM 的核心定位是「通用深度学习编译器」，目标是覆盖从数据中心到端侧的所有硬件。要实现这个目标，就必须把「主机CPU」和「加速设备」解耦为两个独立的编译维度：

- 主机侧：x86、ARM64、ARM32、RISC-V等；
- 设备侧：CUDA、ROCm、OpenCL、Metal、Hexagon、Vulkan等。

通过双目标的自由组合，可以低成本覆盖几十种异构硬件组合，而不需要为每种组合单独开发编译路径。

### 4.5 实践痛点的直接驱动

双目标架构的落地，也直接解决了早期TVM生产落地中的多个共性痛点：

1. **主机侧性能瓶颈**：早期主机侧代码未优化，内存拷贝、预处理、调度的耗时占比甚至超过GPU计算，双目标架构让主机侧代码也能通过LLVM做深度优化，显著降低端到端延迟。
2. **异构部署兼容性差**：不同CPU架构搭配不同加速器的场景下，单目标编译经常出现二进制不兼容、驱动调用失败的问题，双目标通过显式指定两侧架构，从编译层面保证兼容性。
3. **内存管理低效**：主机侧内存分配、页对齐、数据拷贝没有针对目标架构优化，导致显存带宽利用率低；双目标架构下，主机侧内存管理代码可以针对目标CPU的缓存、页大小做定制优化。

---

### 4.6 总结

Host-Device 双目标架构不是一个孤立的语法设计，而是硬件异构化、语义分层、工程部署、架构演进四层因素共同作用的结果。它把经典编译原理中「目标机」的概念做了异构化扩展，将单一编译目标拆分为控制侧与计算侧两个独立目标，既保留了编译器的深度优化能力，又适配了AI时代无处不在的异构计算环境。

## 5 标准使用方式

### 5.1 Python API方式

支持字符串直接构造与配置字典构造两种方式，编译时传入构建流程：

```
import tvm
from tvm import relax

# 字符串形式指定目标
target = tvm.target.Target("llvm -mcpu=core-avx2 -num-threads=8")

# 传入Relax模型编译流程
compiled_model = relax.build(relax_model, target=target)
```

### 5.2 命令行方式（tvmc）

通过TVM命令行工具`tvmc`可直接指定目标完成编译：

```
# 将ONNX模型编译为CUDA目标的动态库
tvmc compile resnet50.onnx \
  --target "cuda -arch=sm_80" \
  --output resnet50_cuda.so
```

## 6 与IR编译栈的层级映射

结合TVM两级IR架构，Target的作用覆盖完整编译流水线：

| IR层级              | Target核心作用                      |
| ----------------- | ------------------------------- |
| Relax IR（图级高层IR）  | 根据硬件特性决定算子融合策略、内存布局转换、算子合法化映射规则 |
| TensorIR（算子级低层IR） | 根据硬件参数执行循环分块、向量化、线程绑定、自动调优等调度优化 |
| 代码生成阶段            | 根据目标类型选择对应后端，生成最终硬件机器码或源代码      |

## 7 编译原理概念映射

对应经典编译原理（龙书）中的核心概念：

- TVM Target ≈ 目标机（Target Machine）
- 多后端代码生成器 ≈ 编译后端的目标代码生成器
- 带`-mtriple`的交叉编译目标 ≈ 交叉编译器的目标三元组
- Target驱动的分层优化 ≈ 与目标机相关的优化阶段
