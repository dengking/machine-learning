# Apache TVM Target 与 Host-Device 双目标架构技术详解

## 摘要

Target（编译目标）是 Apache TVM 编译栈的核心配置对象，其核心设计为 **Host-Device 双目标架构**，以 CUDA 等典型异构计算场景为原生适配对象，用于定义模型部署的硬件环境、指定代码生成后端与运行时约束，驱动从高层计算图到底层硬件代码的全流程定向优化。它是 TVM 实现「一次模型定义，多硬件部署」能力的核心机制，同一份 Relax/Relay 计算图可通过指定不同 Target 配置，编译生成适配不同硬件架构的可执行代码。

---

## 一、Host-Device 双目标架构：从 CUDA 异构场景切入

Host-Device 双目标架构是 TVM 针对异构计算设计的核心目标管理机制，也是所有加速器部署的标准模式。以行业最经典的 CUDA 部署为例，完整的推理程序天然分为**主机侧（CPU）控制逻辑**与**设备侧（GPU）计算逻辑**两部分，二者指令集、内存空间、运行环境完全独立，TVM 的双目标架构正是对这一硬件范式的编译层实现。

### 1.1 从 CUDA 看 Host-Device 的硬件本质

在标准 CUDA 编程模型中，程序天然划分为两个执行域：

- **Host（主机）**：运行在通用 x86/ARM CPU 上，负责内存分配、驱动调用、任务调度、数据预处理、流程控制等串行逻辑，可编程性强、控制灵活。
- **Device（设备）**：运行在 NVIDIA GPU 上，负责核函数（Kernel）的并行张量计算，算力密度高、数据并行度高，是模型推理的性能核心。

二者拥有独立的指令集、内存空间与运行时环境，无法用单一编译目标覆盖。TVM 通过双目标配置分别对两侧进行独立编译与优化，最终链接为完整的可执行程序。

### 1.2 TVM 中的双目标角色分工

#### （1）Device Target（设备端目标）

面向专用计算加速器（GPU、NPU、DSP 等），是模型核心张量计算的执行载体，核心职责：

- 指定加速器对应的代码生成后端，如 `cuda`、`rocm`、`opencl`、`hexagon`、`metal` 等
- 定义加速器的硬件参数（架构版本、计算单元数量、指令集扩展、内存层次），指导 TensorIR 的算子级调度优化（循环分块、向量化、线程映射）
- 生成计算密集型算子的设备端核函数（Kernel），是模型推理性能的核心决定因素

#### （2）Host Target（主机端目标）

面向主 CPU 处理器，是整个推理任务的控制与调度载体，核心职责：

- 生成主机侧控制代码：包括显存/内存分配与拷贝、设备驱动调用接口、算子调度逻辑、参数维度配置
- 负责与设备驱动的交互，完成设备初始化、数据收发、核函数启动等控制操作
- 处理不适合加速器执行的逻辑：控制流分支、标量计算、非加速算子的回退执行

> 
> 关键约束：Host Target 只能是 CPU 类目标（`llvm`、`c` 等），不能是 GPU/加速器目标。

### 1.3 核心工作机制

双目标贯穿 TVM 完整编译栈，两侧并行完成各自的优化与代码生成，最终链接为统一的可执行产物：

| 编译阶段 | 双目标协同逻辑 |
| --- | --- |
| Relax 图级 IR | 根据设备目标特性完成算子拆分、内存布局转换、算子合法化；标记哪些算子卸载（Offload）到设备执行，哪些保留在主机执行 |
| TensorIR 算子级 IR | 设备端目标指导算子的循环分块、向量化、线程块映射；主机端目标优化 CPU 侧的调度逻辑与内存访问模式 |
| 代码生成阶段 | 设备端生成对应后端的核函数代码（如 CUDA Kernel）；主机端生成 CPU 可执行的控制与调度代码 |
| 链接打包阶段 | 将两侧产物与设备运行时库打包，形成完整的可部署模块 |

### 1.4 默认规则与继承关系

1. **自动推断规则**：若仅指定设备端目标，未显式声明 `target_host`，TVM 会自动推断主机端目标——优先使用当前系统的 LLVM CPU 目标，不可用时使用栈虚拟机（stackvm）作为兜底。
2. **纯 CPU 场景合一**：当部署目标就是纯 CPU 时，Host 与 Device 目标合二为一，无需额外区分。
3. **交叉编译覆盖**：交叉编译场景下，主机端目标可以与编译机本身架构不同，通过 `-mtriple` 参数指定目标三元组即可实现跨架构编译。

### 1.5 典型应用场景与代码示例

#### 场景1：异构计算部署（CPU + GPU）

这是最常见的部署模式，以 NVIDIA GPU 推理为例：

- 设备端：GPU 承担所有张量计算，生成 CUDA 核函数
- 主机端：x86 CPU 负责显存管理、驱动调用、流水线调度

```
import tvm

# 主机端目标：x86 Skylake 架构 CPU，支持 AVX512
target_host = tvm.target.Target("llvm -mcpu=skylake-avx512")
# 设备端目标：NVIDIA Ampere 架构 GPU，关联主机目标
target_device = tvm.target.Target("cuda -arch=sm_80", host=target_host)
```

#### 场景2：交叉编译部署（编译机 ≠ 部署机）

在 x86 开发机上编译 ARM 边缘设备的可执行程序，典型如端侧 AI 部署：

- 编译机：x86 架构开发主机
- 部署机：ARM64 架构边缘板卡

```
import tvm

# 目标为 ARM64 Linux 系统，纯 CPU 场景下 host 与 device 合一
target = tvm.target.Target("llvm -mtriple=aarch64-linux-gnu")
```

#### 场景3：端侧异构部署（CPU + DSP）

以高通 Hexagon DSP 的端侧部署为例：

- 设备端：Hexagon DSP 承担神经网络计算
- 主机端：ARM CPU 负责系统调度、数据输入输出

```
import tvm

target_host = tvm.target.Target("llvm -mtriple=aarch64-linux-android")
target_device = tvm.target.Target("hexagon", host=target_host)
```

### 1.6 底层运行时支撑：DeviceAPI 抽象

双目标架构的底层运行时基础是 TVM 的 DeviceAPI 抽象层，它为不同硬件设备提供了统一的操作接口，屏蔽底层硬件差异，支撑上层双目标编译的设备交互逻辑：

- **属性查询**：统一查询设备名称、线程数、显存大小、Warp 大小等硬件参数
- **内存管理**：统一的设备内存分配/释放、主机-设备间数据拷贝接口，区分数据空间与工作空间
- **流管理**：执行流创建、销毁、同步与流间屏障，支撑异步执行与流水线调度
- **标准注册机制**：新硬件可通过统一接口注册 DeviceAPI，快速接入 TVM 编译栈

## 二、Target 的核心功能

Target 贯穿编译全流程，核心承担四类职能：

### 2.1 硬件描述与定向优化

提供目标设备的完整硬件特征描述，包括 CPU 架构、GPU 计算能力、加速器指令集、内存层次结构、核心数量等参数，支撑编译器执行硬件专属的调度优化，如循环分块尺寸、向量化宽度、线程块配置、内存复用策略等。

> 
> NOTE:
> 循环分块参见: [https://www.doubao.com/docx/PGhJdrc1io2DtlxVTgTciW3Pn8g](https://www.doubao.com/docx/PGhJdrc1io2DtlxVTgTciW3Pn8g)

### 2.2 代码生成后端路由

指定编译过程调用的后端代码生成器（如 LLVM、CUDA、OpenCL 等），负责将中间表示（IR）降级为对应硬件的可执行机器码或源代码。不同后端对应不同的硬件生态与指令集，Target 是编译器选择后端的唯一依据。

### 2.3 异构环境隔离与交叉编译

支持 Host（主机）与 Device（设备）双目标分离，区分编译宿主环境与目标执行环境，是交叉编译、异构计算场景的核心支撑。主机端负责调度与内存管理，设备端负责计算密集型算子执行，二者可独立指定目标架构。

### 2.4 全栈优化驱动

Target 的硬件特征会反向驱动两级 IR 的优化策略：

- 图级 IR 阶段：决定算子融合阈值、内存布局转换、算子合法化映射规则
- 算子级 IR 阶段：指导循环分块、并行映射、指令集匹配等调度优化

## 三、主流 Target 类型

TVM 官方支持覆盖 CPU、GPU、嵌入式加速器等多类硬件的目标类型，核心分类如下：

### 3.1 CPU 类目标

| Target 标识 | 技术说明 | 常用配置参数 |
| --- | --- | --- |
| `llvm` | 通用 CPU 后端，基于 LLVM 编译器基础设施生成机器码，原生支持 x86、ARM、RISC-V 等所有 LLVM 兼容架构 | `-mcpu=skylake-avx512`：指定 CPU 型号与指令集   `-mtriple=aarch64-linux-gnu`：交叉编译目标三元组   `-num-threads=8`：运行时 CPU 线程数 |
| `c` | 纯 C 源代码后端，生成可移植的标准 C 代码，适配无 LLVM 支持的嵌入式、微控制器场景 | - |

### 3.2 GPU 类目标

| Target 标识 | 对应硬件平台 | 常用配置参数 |
| --- | --- | --- |
| `cuda` | NVIDIA GPU，生成 CUDA 核函数，适配桌面端、数据中心级 NVIDIA 显卡 | `-arch=sm_80`：指定 GPU 架构版本（如 Ampere 架构对应 sm_80） |
| `rocm` | AMD GPU，基于 ROCm 计算平台，适配 AMD 数据中心与消费级显卡 | - |
| `opencl` | 通用 OpenCL 计算设备，支持各类 GPU、FPGA、嵌入式加速器 | `-device=adreno`：指定高通 Adreno 移动 GPU |
| `metal` | 苹果 Apple Silicon GPU，适配 macOS、iOS 等苹果生态设备 | - |
| `vulkan` | 跨平台 Vulkan 计算后端，同时支持移动端与桌面端 GPU | - |
| `webgpu` | 浏览器端 WebGPU 计算后端，适配 Web 端推理场景 | - |
| `mali` / `bifrost` | ARM Mali 系列移动 GPU，适配移动端嵌入式场景 | - |

### 3.3 嵌入式与专用加速器

- `hexagon`：高通 Hexagon DSP，适配移动端低功耗计算场景
- `stm32`：STM32 系列微控制器，属于 microTVM 嵌入式生态
- `arm_compute_lib`：ARM Compute Library 算子加速库，以 BYOC 模式接入
- `tensorrt` / `cudnn`：NVIDIA TensorRT / cuDNN 推理引擎，以 BYOC 扩展模式接入
- 第三方 NPU/DPU 目标：如赛灵思 Vitis AI DPU 等厂商定制加速目标

## 四、Host-Device 双目标架构的设计背景

Host-Device 双目标架构并非孤立的设计，而是硬件异构化趋势、软件语义分层、全场景部署需求、TVM 自身架构演进共同驱动的必然结果，本质是将经典编译原理中「目标机」的概念，细化为「控制侧目标机 + 计算侧目标机」的两级结构，适配异构计算时代的编译需求。

### 4.1 硬件产业背景：异构计算成为 AI 部署的标准范式

#### 4.1.1 算力分工的固化：通用CPU + 专用加速器

AI 模型的计算特征天然形成了两层分工，直接决定了硬件的异构形态：

- **计算密集型张量运算**：矩阵乘、卷积、向量元素操作等，数据并行度高、控制逻辑简单，适合由 GPU、NPU、DSP、TPU 等专用加速器执行，追求高吞吐量、高算力密度。
- **控制与调度逻辑**：内存分配与拷贝、驱动调用、流程控制、分支判断、动态形状处理、前后预处理等，串行性强、逻辑复杂，适合由通用 CPU 执行，追求低延迟、强通用性。

这种分工是整个行业的事实标准：从数据中心的「x86 CPU + NVIDIA GPU」，到边缘端的「ARM CPU + NPU/DSP」，再到端侧手机的「ARM CPU + Mali/Adreno GPU」，无一例外都是异构组合。单一指令集的硬件无法同时兼顾计算效率与控制灵活性，这是双目标架构最底层的硬件基础。

#### 4.1.2 单目标编译的天然缺陷

如果编译器只支持单一目标，会直接出现两个不可调和的问题：

- 若目标为加速器：只能生成计算核函数，主机侧的控制、调度、内存管理逻辑只能靠手写胶水代码对接，既无法做编译期优化，也无法保证跨架构兼容性。
- 若目标为 CPU：无法利用加速器的算力，模型推理性能差一个数量级，完全丧失 AI 加速的意义。

双目标架构的核心设计初衷，就是让编译器同时面向两个不同的目标机生成代码，分别负责控制逻辑与计算逻辑，二者协同完成端到端推理。

### 4.2 软件语义背景：计算流与控制流的天然分层

#### 4.2.1 深度学习模型的语义分层

深度学习模型的代码语义天然分为两个层级，对应不同的执行载体：

- **算子级计算流**：纯数据并行、无副作用的张量运算，是模型的核心计算主体，适合卸载到加速器执行。
- **图级控制流**：条件分支、循环、动态形状推导、内存布局转换、算子调度、错误处理等，属于控制逻辑，串行执行且存在副作用，更适合在通用 CPU 上运行。

#### 4.2.2 与 TVM 两级 IR 架构的对应

TVM 的 Relax（图级 IR）+ TensorIR（算子级 IR）两层架构，天然匹配这种语义分层，也直接要求双目标编译的支撑：

- **Relax 层**：负责描述计算图拓扑、控制流、内存布局，其编译优化与代码生成对应主机侧目标——决定算子如何调度、内存如何管理、控制流如何执行。
- **TensorIR 层**：负责描述算子内部的循环结构、并行映射、指令匹配，其编译优化与代码生成对应设备侧目标——决定单个算子如何在加速器上高效执行。

如果没有双目标架构，两层 IR 就只能面向同一种硬件，既浪费了图级 IR 对控制逻辑的优化能力，也限制了算子级 IR 对加速器的深度适配。

#### 4.2.3 算子卸载（Offloading）的标准化

异构计算的核心是「计算卸载」：把适合加速器的算子从主机逻辑中剥离，放到设备端执行。双目标架构为卸载提供了标准化的编译边界：

- 编译期自动标记可卸载算子，按目标拆分编译单元；
- 主机侧生成卸载调度、数据收发的代码；
- 设备侧生成算子核函数代码；
- 两侧通过标准运行时接口交互，无需手动胶水代码。

### 4.3 工程部署背景：交叉编译与全场景部署的刚需

#### 4.3.1 开发与部署环境的分离

AI 部署的典型工程范式是「中心化编译，分布式部署」：

- 编译环境：通常是 x86 架构的高性能开发服务器，算力充足、工具链完整；
- 部署环境：可能是 ARM 架构的边缘板卡、嵌入式设备、手机端，算力有限、环境受限，不具备本地编译能力。

这就要求编译器必须支持交叉编译：在一种架构的主机上，编译出另一种架构的可执行代码。

- 传统单目标交叉编译只能解决「设备端代码」的跨架构生成，忽略了「主机端控制代码」也需要匹配部署端的 CPU 架构。
- 双目标架构可以同时指定主机端目标架构与设备端目标架构，一次性编译出完整的、可直接在目标异构环境运行的程序。

#### 4.3.2 嵌入式与端侧部署的强约束

在嵌入式、物联网、端侧场景下，部署环境的约束极强：

- 硬件资源受限，无法安装完整的编译工具链与依赖库；
- CPU 架构多样（ARMv7、ARMv8、RISC-V 等），搭配的加速器类型千差万别；
- 对二进制体积、启动延迟、内存占用有严格要求。

双目标架构可以精准匹配每一种「CPU + 加速器」的硬件组合，针对目标环境做极致优化，同时完全不需要部署端具备编译能力，这是 TVM 能够覆盖全场景部署的核心工程基础。

### 4.4 TVM 自身架构演进的必然结果

#### 4.4.1 早期单目标架构的局限

TVM 早期版本只支持单一目标配置，存在三个明显缺陷：

1. **主机侧架构默认绑定本地系统**：编译时自动使用编译机的 CPU 架构作为主机端目标，交叉编译场景下会生成错误架构的主机代码，无法在部署端运行。
2. **主机侧代码无优化**：主机侧的内存管理、调度逻辑、驱动交互代码默认生成，不做针对性优化，经常成为端到端推理的性能瓶颈。
3. **异构组合扩展性差**：每新增一种「CPU + 加速器」组合，都需要修改编译流程代码，无法通过配置化的方式快速适配。

#### 4.4.2 运行时分层设计的倒逼

TVM 的运行时（Runtime）本身就是分层设计：

- **主机运行时**：负责模块管理、函数调度、内存分配、设备驱动抽象，运行在通用 CPU 上；
- **设备运行时**：负责核函数执行、设备内存管理，运行在加速器上。

编译作为运行时的上游，必须对应分层的运行时架构，分别生成适配两侧的目标代码，否则运行时的分层设计就失去了编译优化的支撑。双目标架构本质是「分层运行时」在编译期的镜像。

#### 4.4.3 全硬件生态覆盖的定位

TVM 的核心定位是「通用深度学习编译器」，目标是覆盖从数据中心到端侧的所有硬件。要实现这个目标，就必须把「主机 CPU」和「加速设备」解耦为两个独立的编译维度：

- 主机侧：x86、ARM64、ARM32、RISC-V 等；
- 设备侧：CUDA、ROCm、OpenCL、Metal、Hexagon、Vulkan 等。

通过双目标的自由组合，可以低成本覆盖几十种异构硬件组合，而不需要为每种组合单独开发编译路径。

### 4.5 实践痛点的直接驱动

双目标架构的落地，也直接解决了早期 TVM 生产落地中的多个共性痛点：

1. **主机侧性能瓶颈**：早期主机侧代码未优化，内存拷贝、预处理、调度的耗时占比甚至超过 GPU 计算，双目标架构让主机侧代码也能通过 LLVM 做深度优化，显著降低端到端延迟。
2. **异构部署兼容性差**：不同 CPU 架构搭配不同加速器的场景下，单目标编译经常出现二进制不兼容、驱动调用失败的问题，双目标通过显式指定两侧架构，从编译层面保证兼容性。
3. **内存管理低效**：主机侧内存分配、页对齐、数据拷贝没有针对目标架构优化，导致显存带宽利用率低；双目标架构下，主机侧内存管理代码可以针对目标 CPU 的缓存、页大小做定制优化。

### 4.6 小结

Host-Device 双目标架构不是一个孤立的语法设计，而是硬件异构化、语义分层、工程部署、架构演进四层因素共同作用的结果。它把经典编译原理中「目标机」的概念做了异构化扩展，将单一编译目标拆分为控制侧与计算侧两个独立目标，既保留了编译器的深度优化能力，又适配了 AI 时代无处不在的异构计算环境。

## 五、标准使用方式

### 5.1 Python API 方式

支持字符串直接构造与配置字典构造两种方式，编译时传入构建流程：

```
import tvm
from tvm import relax

# 字符串形式指定目标
target = tvm.target.Target("llvm -mcpu=core-avx2 -num-threads=8")

# 传入 Relax 模型编译流程
compiled_model = relax.build(relax_model, target=target)
```

### 5.2 命令行方式（tvmc）

通过 TVM 命令行工具 `tvmc` 可直接指定目标完成编译：

```
# 将 ONNX 模型编译为 CUDA 目标的动态库
tvmc compile resnet50.onnx \
  --target "cuda -arch=sm_80" \
  --output resnet50_cuda.so
```

## 六、与两级 IR 编译栈的层级映射

结合 TVM 两级 IR 架构，Target 的作用覆盖完整编译流水线：

| IR 层级 | Target 核心作用 |
| --- | --- |
| Relax IR（图级高层 IR） | 根据硬件特性决定算子融合策略、内存布局转换、算子合法化映射规则 |
| TensorIR（算子级低层 IR） | 根据硬件参数执行循环分块、向量化、线程绑定、自动调优等调度优化 |
| 代码生成阶段 | 根据目标类型选择对应后端，生成最终硬件机器码或源代码 |

## 七、编译原理概念映射

对应经典编译原理（龙书）中的核心概念：

- TVM Target ≈ 目标机（Target Machine）
- 多后端代码生成器 ≈ 编译后端的目标代码生成器
- 带 `-mtriple` 的交叉编译目标 ≈ 交叉编译器的目标三元组
- Target 驱动的分层优化 ≈ 与目标机相关的优化阶段
